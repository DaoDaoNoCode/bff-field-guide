# Tutorial 2: POST with Body Validation

In the last tutorial, you built a GET endpoint that returns data. Now you are going the other direction -- the frontend is sending data *to* you. You will build a POST endpoint that accepts a JSON request body, validates every field, and returns structured error messages when something is wrong.

This is the most common pattern in BFF development. Every form submission, every resource creation, every configuration update goes through a handler that does exactly what you are about to build.

**Time:** ~25 minutes

**Prerequisite:** Complete [Tutorial 1: Your First GET Endpoint](./first-get-endpoint).

## What You Are Building

A `POST /api/v1/feedback` endpoint that accepts user feedback. The React frontend would send this request:

```json
{
  "category": "bug",
  "message": "The model list page is slow",
  "severity": 3
}
```

And your handler would validate the input, process it, and respond with:

```json
{
  "data": {
    "id": "fb-1705000000",
    "category": "bug",
    "message": "The model list page is slow",
    "severity": 3,
    "status": "received"
  }
}
```

Your handler will enforce these rules:
- `category` must be one of: `"bug"`, `"feature"`, `"general"` -- anything else is rejected
- `message` must not be empty and must not exceed 1000 characters
- `severity` must be between 1 and 5

Any violation returns a `400 Bad Request` with a clear error message.

## Step 1: Define the Request and Response Models

In TypeScript, you might write one interface and use `Omit` to create a request type:

```typescript
interface Feedback {              // The full feedback object
  id: string;                     // Generated by the server
  category: string;               // User-provided category
  message: string;                // User-provided message
  severity: number;               // User-provided severity 1-5
  status: string;                 // Set by the server ("received")
}

// Request is a subset -- no id, no status
type FeedbackRequest = Omit<Feedback, 'id' | 'status'>;
```

In Go, the convention is simpler: define two separate structs. No generics gymnastics. No utility types. Just two plain structs.

Create `packages/automl/bff/internal/models/feedback.go`:

```go
package models                         // Must match the directory name

// FeedbackRequest represents the incoming JSON body for submitting feedback.
// This is what the frontend sends to us.
type FeedbackRequest struct {          // Exported (uppercase) so the handler package can use it
	Category string `json:"category"`  // Maps to "category" in the JSON body
	Message  string `json:"message"`   // Maps to "message" in the JSON body
	Severity int    `json:"severity"`  // Maps to "severity" -- int, not float64
}

// FeedbackResponse represents the response after feedback is accepted.
// This is what we send back to the frontend.
type FeedbackResponse struct {         // Separate struct -- Go convention for request vs response
	ID       string `json:"id"`        // Generated by the server (not in the request)
	Category string `json:"category"`  // Echo back what they sent
	Message  string `json:"message"`   // Echo back what they sent
	Severity int    `json:"severity"`  // Echo back what they sent
	Status   string `json:"status"`    // Set by the server -- always "received" for now
}
```

::: info Two Structs, Not One
In TypeScript, you might reach for `Omit<>` or `Pick<>` to derive one type from another. In Go, it is idiomatic to define separate structs for request and response. They have zero runtime cost (no class instantiation, no prototype chain), they are self-documenting (you can see exactly what each shape looks like), and they avoid the confusion that comes from one interface trying to serve two purposes.
:::

**What you should see:** Save the file. Zero errors.

## Step 2: Write the Validation Function

Before writing the handler, let's write the validation logic as a standalone function. We are doing this separately because:
1. It keeps the handler clean -- the handler's job is request/response flow, not business rules
2. Standalone functions are easy to unit test without constructing an entire `App`

Add this to a new file, or we will put it in the handler file in the next step. For now, understand the pattern:

In TypeScript, you might validate like this:

```typescript
function validateFeedback(input: FeedbackRequest): string | null {  // Returns error message or null
  if (!input.category) return 'category is required';               // Check for empty string
  if (!['bug', 'feature', 'general'].includes(input.category)) {   // Check allowed values
    return 'category must be one of: bug, feature, general';
  }
  if (!input.message) return 'message is required';                 // Check for empty string
  if (input.message.length > 1000) return 'message too long';      // Check max length
  if (input.severity < 1 || input.severity > 5) return 'invalid';  // Check range
  return null;                                                      // null means valid
}
```

## Step 3: Write the Handler

Create `packages/automl/bff/internal/api/feedback_handler.go`:

```go
package api                                  // This file belongs to the api package

import (                                     // All imports in one block
	"fmt"                                    // Formatting -- fmt.Errorf creates error messages
	"net/http"                               // HTTP status codes and types
	"time"                                   // Time operations for generating IDs

	"github.com/julienschmidt/httprouter"    // The router -- provides the handler signature
	"github.com/opendatahub-io/automl-library/bff/internal/models"  // Our request/response structs
)

// FeedbackEnvelope wraps the feedback response in the standard { "data": ... } envelope.
type FeedbackEnvelope Envelope[*models.FeedbackResponse, None]  // Same pattern as Tutorial 1

// validCategories defines the allowed feedback categories.
// Using a map[string]bool is Go's idiomatic "set" -- checking membership is O(1).
// In TypeScript you might use: const validCategories = new Set(["bug", "feature", "general"])
var validCategories = map[string]bool{       // Package-level variable -- initialized once
	"bug":     true,                         // "bug" is a valid category
	"feature": true,                         // "feature" is a valid category
	"general": true,                         // "general" is a valid category
}

// CreateFeedbackHandler accepts user feedback, validates it, and returns a confirmation.
// This follows the standard POST handler pattern:
//   1. Read the JSON body
//   2. Validate the input
//   3. Process the request
//   4. Write the response
func (app *App) CreateFeedbackHandler(w http.ResponseWriter, r *http.Request, _ httprouter.Params) {
	// ── Step 1: Read the JSON body into our request struct ──

	var input models.FeedbackRequest           // Declare a variable of type FeedbackRequest
	                                           // At this point, all fields are zero values ("", 0)
	err := app.ReadJSON(w, r, &input)          // ReadJSON deserializes the request body into input
	                                           // The & means "pass the memory address" so ReadJSON
	                                           // can fill in the values (like pass-by-reference)
	if err != nil {                            // If the JSON was malformed, wrong type, etc.
		app.badRequestResponse(w, r, err)      // Write a 400 error with the message
		return                                 // CRITICAL: stop here! Without this return,
		                                       // the rest of the handler keeps running
	}

	// ── Step 2: Validate the input fields ──

	if err := validateFeedback(&input); err != nil {  // Call our validation function
		app.badRequestResponse(w, r, err)              // If invalid, write 400 with the error message
		return                                         // Stop -- don't process invalid input
	}

	// ── Step 3: Process the feedback ──
	// In a real handler, you would save to a database, call an upstream service, etc.
	// For this tutorial, we just echo back the input with a generated ID and status.

	response := &models.FeedbackResponse{              // Build the response struct
		ID:       fmt.Sprintf("fb-%d", time.Now().Unix()),  // Generate an ID from the Unix timestamp
		Category: input.Category,                      // Echo back the category they sent
		Message:  input.Message,                       // Echo back the message they sent
		Severity: input.Severity,                      // Echo back the severity they sent
		Status:   "received",                          // Server-set field -- always "received"
	}

	// ── Step 4: Write the response ──

	envelope := FeedbackEnvelope{              // Wrap in the standard envelope
		Data: response,                        // { "data": { "id": "fb-...", ... } }
	}
	err = app.WriteJSON(w, http.StatusCreated, envelope, nil)  // 201 Created, not 200 OK
	                                                            // POST endpoints that create
	                                                            // a resource return 201
	if err != nil {                            // If JSON serialization somehow fails
		app.serverErrorResponse(w, r, err)     // Write a 500 error
	}
}

// validateFeedback checks all fields of the feedback request.
// It returns an error describing the first validation failure,
// or nil if everything is valid.
//
// This is a standalone function, NOT a method on App.
// It doesn't need the logger, config, or any other dependency.
// That makes it trivially easy to unit test.
func validateFeedback(input *models.FeedbackRequest) error {  // Takes a pointer to avoid copying
	// Check category is present
	if input.Category == "" {                  // In Go, the zero value for string is ""
		return fmt.Errorf("category is required")  // Return an error with this message
	}
	// Check category is one of the allowed values
	if !validCategories[input.Category] {      // Map lookup: returns false if key doesn't exist
		return fmt.Errorf("category must be one of: bug, feature, general")
	}

	// Check message is present
	if input.Message == "" {                   // Empty string check
		return fmt.Errorf("message is required")
	}
	// Check message length
	if len(input.Message) > 1000 {             // len() works on strings, slices, and maps
		return fmt.Errorf("message must not exceed 1000 characters")
	}

	// Check severity range
	if input.Severity < 1 || input.Severity > 5 {  // Range check -- same as TypeScript
		return fmt.Errorf("severity must be between 1 and 5")
	}

	return nil                                 // nil means "no error" -- everything is valid
	                                           // Like returning null from a function that
	                                           // returns Error | null in TypeScript
}
```

::: warning The `return` After Error Is Critical
This is the #1 mistake TypeScript developers make in Go handlers. In Express, `res.json()` ends the response. In Go, `app.badRequestResponse()` writes the error response but does **not** stop your function. You must `return` explicitly, or the rest of the handler keeps running and tries to write a second response -- which causes a panic.

```go
// WRONG -- missing return
if err != nil {
    app.badRequestResponse(w, r, err)  // Writes 400 error...
}
// ...but execution continues here and tries to write a 201!

// RIGHT -- return after error
if err != nil {
    app.badRequestResponse(w, r, err)  // Writes 400 error
    return                              // Stops the handler
}
```
:::

## Step 4: Register the Route

Open `packages/automl/bff/internal/api/app.go` again. Add the path constant:

```go
const (
	// ... existing constants ...
	DetailedHealthCheckPath = ApiPathPrefix + "/healthcheck/detailed"  // From Tutorial 1
	FeedbackPath            = ApiPathPrefix + "/feedback"              // ADD THIS LINE
	UserPath                = ApiPathPrefix + "/user"
	// ...
)
```

And add the route registration inside `Routes()`, after your healthcheck route:

```go
	// Feedback endpoint -- POST, no namespace required for this example
	apiRouter.POST(FeedbackPath, app.CreateFeedbackHandler)  // ADD THIS LINE
	                                                          // Notice: POST, not GET
```

::: info Why `apiRouter.POST` Instead of `apiRouter.GET`?
`httprouter` enforces HTTP method matching. If someone sends a GET request to `/api/v1/feedback`, they will get a `405 Method Not Allowed` response automatically. You do not need to write any code for that -- the `MethodNotAllowed` handler at the top of `Routes()` handles it.
:::

```bash

```

You did not write any of that JSON parsing or error formatting code. The `ReadJSON` helper in `helpers.go` handles syntax errors, type mismatches, body-too-large, multiple JSON values, unknown fields, and empty bodies. You get all of that for free in every handler that calls `app.ReadJSON()`.
:::

### The POST Handler Pattern

Every POST handler in every BFF follows this exact structure. Memorize it:

```
1. Read the JSON body     -> app.ReadJSON(w, r, &input)
2. Validate the input     -> validateSomething(&input)
3. Process the request    -> call upstream service, save to database, etc.
4. Write the response     -> app.WriteJSON(w, statusCode, envelope, nil)
```

Each step can fail. Each failure writes an error response and returns immediately. That is the entire pattern.
